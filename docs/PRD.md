| 项目 | 内容 |

| 项目编号 | 项目 11 |

## 2. 项目背景

企业在销售、运营、财务、库存等场景中沉淀了大量结构化数据，但业务人员通常需要依赖数据分析师编写 SQL、制作图表和整理报告，导致数据查询和经营分析链路较长。传统 BI 工具虽然能展示仪表盘，但对自然语言提问、自动洞察生成、异常原因解释和周期性报告生成的支持不足。

本项目希望构建一个智能 BI 平台，让业务用户可以用日常语言查询数据，系统自动理解业务指标、生成 SQL、展示图表、解释结果，并进一步完成报告生成、异常归因和趋势预测，降低业务分析门槛，提高数据决策效率。

## 3. 项目目标

### 3.1 总体目标

构建一个面向企业经营分析场景的智能 BI 数据洞察平台，实现“自然语言提问 -> 自动数据查询 -> 可视化展示 -> 洞察解释 -> 报告输出”的闭环。

### 3.2 阶段目标

1. 完成可导入示例业务数据的数据分析环境。
2. 实现自然语言转 SQL 查询能力，并展示查询结果。
3. 支持常见图表展示和多维筛选。
4. 支持基于模板的周报、月报自动生成。
5. 支持关键指标异常检测和自然语言归因说明。
6. 支持基础趋势预测和假设分析演示。

## 4. 用户角色

| 角色 | 说明 | 主要诉求 |
| --- | --- | --- |
| 业务人员 | 不熟悉 SQL 的一线业务用户 | 用自然语言快速查询销售、收入、产品、区域等指标 |
| 数据分析师 | 负责数据口径、报表和分析支持 | 管理数据表、指标口径、SQL 结果和报告模板 |
| 部门管理者 | 关注经营结果和趋势 | 查看核心指标、异常提醒、趋势预测和周期报告 |
| 系统管理员 | 负责系统配置和权限 | 管理用户、数据源、指标字典和访问权限 |

## 5. 业务范围

### 5.1 本期范围

本期建议围绕一个可控的示例业务数据集展开，例如电商销售数据、区域产品销售数据或门店经营数据，重点覆盖以下业务对象：

- 销售订单
- 产品
- 区域
- 客户
- 时间维度
- 销售额、订单量、客单价、收入、毛利等指标

### 5.2 暂不纳入范围

- 多租户企业级权限体系。
- 复杂实时数仓建设。
- 训练自有大模型。
- 复杂财务合规报表。
- 面向生产环境的大规模性能压测。

## 6. 功能需求

### 6.1 数据源与数据管理

#### 6.1.1 示例数据导入

系统应支持导入或初始化一套结构化业务数据，至少包括销售订单、产品、区域和时间字段。

验收标准：

- 系统内存在可查询的示例数据。
- 数据表字段、含义和指标口径可查看。
- 查询功能可以基于示例数据返回结果。

#### 6.1.2 指标字典管理

系统应维护常用业务指标的名称、计算方式和适用表字段，例如销售额、订单量、客单价、同比、环比。

验收标准：

- 能查看指标名称、指标说明和计算口径。
- 自然语言查询时可引用指标字典进行语义匹配。
- 指标口径变更后，查询解释同步更新。

### 6.2 自然语言数据查询

#### 6.2.1 自然语言问题输入

用户可在查询框中输入日常语言问题，例如：

- 上月华东区销售额最高的产品是什么？
- 最近 30 天销售额趋势如何？
- 哪个区域的订单量下降最明显？
- 本月客单价最高的前 10 个产品是什么？

验收标准：

- 支持中文自然语言输入。
- 系统能识别时间、区域、产品、指标、排序、聚合等查询意图。
- 对无法理解的问题给出明确提示，而不是返回错误堆栈。

#### 6.2.2 Text-to-SQL 转换

系统应将自然语言问题转换为可执行 SQL，并在执行前进行安全校验。

验收标准：

- 生成 SQL 仅允许执行只读查询。
- SQL 中不得包含删除、修改、建表、授权等高风险语句。
- 查询结果应与用户问题基本一致。
- 前端可展示生成的 SQL 或查询解释，便于检查。

#### 6.2.3 查询结果展示

系统应以表格、图表和自然语言摘要展示查询结果。

验收标准：

- 数值型结果可用表格展示。
- 时间序列结果可用折线图展示。
- 分类对比结果可用柱状图或饼图展示。
- 系统能生成一句到数句查询结论。

### 6.3 多维分析与可视化交互

#### 6.3.1 维度筛选

用户可按时间、区域、产品类别、客户类型等维度筛选数据。

验收标准：

- 筛选条件变化后，图表和表格同步刷新。
- 筛选条件在页面中清晰展示。
- 支持清空筛选和重新查询。

#### 6.3.2 多维下钻

用户可从总览指标进一步下钻到区域、产品、月份等维度。

验收标准：

- 支持从总销售额下钻到区域贡献。
- 支持从区域下钻到产品贡献。
- 下钻路径可返回上一级。

#### 6.3.3 图表导出

系统应支持导出查询结果或报告内容。

验收标准：

- 支持导出查询结果为 CSV。
- 支持导出报告为 Markdown 或 PDF。
- 导出内容包含查询条件和生成时间。

### 6.4 自动报告生成

#### 6.4.1 周报和月报生成

系统应基于预设模板和业务数据生成周期性分析报告。

报告应包含：

- 报告标题和统计周期。
- 核心指标概览。
- 指标变化说明。
- 关键图表。
- 异常或亮点说明。
- 结论和建议。

验收标准：

- 用户可选择周报或月报。
- 系统自动填充指标、图表和文字分析。
- 报告内容可预览和导出。

#### 6.4.2 自定义报告结构

用户可选择报告模块，例如销售概览、区域分析、产品排行、异常指标、趋势预测。

验收标准：

- 用户可勾选需要的报告模块。
- 生成报告按用户选择的结构组织内容。
- 报告模板可以保存为配置。

### 6.5 异常检测与归因分析

#### 6.5.1 关键指标监控

系统应监控销售额、订单量、客单价等关键指标的异常波动。

验收标准：

- 可配置监控指标。
- 系统能识别明显高于或低于历史均值的异常点。
- 异常点在图表中有明确标记。

#### 6.5.2 异常归因说明

系统应结合维度拆解结果，用自然语言解释异常可能原因。

验收标准：

- 异常说明包含发生时间、异常指标、变化幅度和可能原因。
- 支持按区域、产品、客户类型等维度分析贡献。
- 说明中应区分“数据支持的结论”和“系统推测”。

### 6.6 趋势预测与假设分析

#### 6.6.1 趋势预测

系统应基于历史数据预测未来一段时间的销售额、订单量或收入趋势。

验收标准：

- 支持选择预测指标。
- 支持展示历史趋势和预测趋势。
- 明确标注预测结果仅供参考。

#### 6.6.2 假设分析

用户可通过自然语言进行业务模拟，例如：

- 如果华东区促销投入增加 10%，预计销售额会怎样变化？
- 如果某产品价格下降 5%，可能影响多少收入？

验收标准：

- 系统能识别假设条件、影响指标和分析范围。
- 返回模拟结果和解释。
- 对缺少数据支撑的假设给出限制说明。

### 6.7 用户与权限

本期可采用简化权限模型。

验收标准：

- 支持普通用户和管理员两类角色。
- 普通用户可查询、查看图表和生成报告。
- 管理员可管理数据源、指标字典和报告模板。

## 7. 非功能需求

### 7.1 易用性

- 查询入口应简单直接。
- 图表、表格和文字解释应在同一分析页面中呈现。
- 对错误问题、无数据结果和 SQL 生成失败提供可理解提示。

### 7.2 安全性

- Text-to-SQL 执行前必须进行只读校验。
- 数据库账号应采用最小权限。
- 不在前端暴露数据库连接信息和大模型密钥。
- 用户导出的报告不得包含无权限数据。

### 7.3 可解释性

- 系统应展示查询理解结果、生成 SQL 或查询依据。
- 对异常归因和预测结果应说明依据与限制。
- 报告中的关键结论应能追溯到数据结果。

### 7.4 性能

- 常规查询应在 5 秒内返回结果。
- 报告生成应在 30 秒内完成。
- 图表交互应无明显卡顿。

### 7.5 可扩展性

- 数据源接入、指标字典、报告模板和模型调用应模块化。
- 后续可扩展更多业务数据表和更多图表类型。

## 8. 系统架构建议

### 8.1 架构分层

1. 前端层
   - 使用 Vue.js 构建查询页、仪表盘页、报告页和配置页。

2. 后端接口层
   - 建议使用 FastAPI 提供 REST API。
   - 负责用户请求、数据查询、报告生成和权限校验。

3. AI 能力层
   - Text-to-SQL 模块：将自然语言转换为 SQL。
   - 洞察生成模块：根据查询结果生成自然语言分析。
   - 异常归因模块：结合指标波动和维度拆解生成解释。
   - 报告生成模块：基于模板生成周报、月报和自定义报告。
   - Agent 编排模块：协调查询、分析、图表和报告任务。

4. 数据层
   - MySQL 8.0 存储业务数据、指标字典、报告模板和用户配置。

5. 部署层
   - Nginx 用于静态资源服务和后端反向代理。

### 8.2 推荐模块

| 模块 | 职责 |
| --- | --- |
| Query Parser | 解析自然语言问题，识别指标、维度、时间和筛选条件 |
| SQL Generator | 生成 SQL 并执行安全校验 |
| Data Service | 查询 MySQL 并返回结构化结果 |
| Chart Service | 根据结果推荐图表类型 |
| Insight Service | 生成自然语言分析结论 |
| Report Service | 生成和导出分析报告 |
| Anomaly Service | 识别指标异常并进行维度归因 |
| Forecast Service | 提供基础趋势预测 |

## 11. 关键流程

### 11.1 自然语言查询流程

1. 用户输入问题。
2. 系统解析问题中的指标、时间、维度和筛选条件。
3. 系统匹配指标字典和数据表结构。
4. 系统生成只读 SQL。
5. 系统执行 SQL 并返回结果。
6. 系统推荐图表类型。
7. 系统生成自然语言摘要。
8. 前端展示表格、图表和结论。

### 11.2 自动报告生成流程

1. 用户选择报告类型和时间范围。
2. 用户选择报告模块。
3. 系统查询对应指标数据。
4. 系统生成图表和核心洞察。
5. 系统按模板组织报告内容。
6. 用户预览、调整并导出报告。

### 11.3 异常归因流程

1. 系统监控关键业务指标。
2. 系统识别异常波动。
3. 系统按时间、区域、产品等维度拆解贡献。
4. 系统生成异常原因说明。
5. 用户查看异常详情并导出分析结果。

## 13. 验收标准

项目完成时应满足：

1. 用户可以输入自然语言问题并获得正确查询结果。
2. 系统可以展示表格、图表和自然语言摘要。
3. 系统可以生成至少一种周期性报告。
4. 系统可以识别至少一种指标异常并给出归因说明。
5. 系统可以展示至少一种趋势预测结果。
6. 系统可以导出查询结果或报告。
7. 项目代码结构清晰，文档完整，可运行演示。

## 14. 风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| Text-to-SQL 结果不稳定 | SQL 语义错误或无法执行 | 限定示例数据表，使用指标字典和 SQL 校验 |
| 业务指标口径不清 | 查询结果和用户理解不一致 | 建立指标字典，展示查询解释 |
| 报告内容空泛 | 只有模板文字，缺少数据支撑 | 报告结论必须绑定查询结果和图表 |
| 预测结果误导 | 用户把预测当作确定结论 | 明确标注预测仅供参考，展示历史数据依据 |
| 2 周周期过短 | 功能过多导致无法完成 | 优先实现自然语言查询、图表展示和报告生成，异常归因和预测做演示版 |

## 15. MVP 范围建议

若以 2 周实习项目为交付周期，建议 MVP 保留：

- 示例销售数据集。
- 自然语言转 SQL 查询。
- SQL 只读安全校验。
- 表格与 3 类基础图表展示。
- 周报或月报生成。
- 简单异常检测。
- 简单趋势预测。
- Markdown 或 PDF 报告导出。

可延后：

- 多数据源接入。
- 完整权限体系。
- 复杂 Agent 工作流。
- 企业级报表模板管理。
- 高级预测模型。
