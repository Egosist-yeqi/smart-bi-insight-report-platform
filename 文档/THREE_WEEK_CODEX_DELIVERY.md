# 三周 Codex 辅助开发交付说明

## 使用方式

本说明用于答辩时介绍三周内的开发组织方式和交付范围。它描述的是本仓库可核验的代码、文档、测试和运行结果，不把 Codex 的辅助工作包装成无法复现的“黑盒成果”。答辩时可结合 Git 提交记录、GitHub 仓库和系统现场演示说明。

## 第 1 周：需求、数据与基础架构

| 工作项 | 交付物 | 可展示证据 |
| --- | --- | --- |
| 需求梳理 | 项目说明、PRD、页面与接口范围 | `文档/` 下的需求与过程文档。 |
| 数据建模 | 销售订单、指标、报告模板、查询历史和 AI 配置表 | MySQL 初始化与迁移脚本。 |
| 基础工程 | React 前端、FastAPI 后端、MySQL、Docker Compose | `compose.yaml`、前后端目录和启动器。 |
| 演示数据 | 540 条可重复初始化的销售订单 | 健康接口和仪表盘订单数。 |

这一周的重点是先做出可运行骨架，而不是只画页面。Codex 可辅助生成工程结构、检查接口一致性、补充种子数据和把需求拆成可验证任务。

## 第 2 周：分析能力与用户工作流

| 工作项 | 交付物 | 可展示证据 |
| --- | --- | --- |
| 仪表盘与筛选 | KPI、趋势、区域贡献、产品排行 | 现场切换“华东”筛选。 |
| 自然语言查询 | 本地规则解析、查询意图、只读 SQL、图表和 CSV | 输入示例问题与查询历史。 |
| 报告生成 | 月报模块选择、预览、Markdown 导出 | 下载报告文件。 |
| 异常和预测 | 阈值异常提示、归因证据、OLS 趋势预测 | 异常页与趋势页。 |

这一周的重点是把“数据能查到”变为“业务人员能完成一轮分析工作”。Codex 的价值在于协助快速迭代前后端联调、补齐边界状态和整理演示问题，而不是替代业务口径的确认。

## 第 3 周：AI 接入、安全、测试与答辩交付

| 工作项 | 交付物 | 可展示证据 |
| --- | --- | --- |
| 用户自有 API | 加密保存、脱敏展示、连接测试、删除配置 | 系统配置页与测试接口。 |
| DeepSeek 体验 | 默认预设仅需输入 Key；JSON 模式与思考标签兼容 | DeepSeek 连接测试、客户端单元测试。 |
| 安全边界 | DNS/重定向限制、私网显式授权、只读 SQL、AI 回退 | 后端测试和答辩讲解。 |
| 可复现性 | 一键启动、停止脚本、README、演示素材 | 根目录 `.cmd` 与 `文档/demo/`。 |
| 质量验证 | 后端测试、前端单测、生产构建、浏览器验收脚本 | `scripts/test.ps1` 与测试报告。 |

这一周的重点是把原型收束成他人可启动、可测试、可讲解的系统。Codex 可以高效处理重复性工作，例如测试用例扩展、文档一致性检查、启动脚本和问题排查；最终业务逻辑、演示口径和 API Key 仍由项目负责人确认。

## 答辩中的推荐表述

“我把三周工作拆成可复现的三个阶段：第一周完成数据和全栈基础设施，第二周完成查询、报告和分析工作流，第三周把用户自有 AI 接入、安全校验、自动化测试和答辩材料补齐。Codex 主要用来加快代码实现、联调、测试与文档整理；每一项最终都落在 GitHub 仓库、Docker 可运行系统和自动化测试中，因此可以现场验证。”

## 不建议的表述

- 不建议声称模型生成的所有代码都天然正确。
- 不建议把 API Key、私有提示词或聊天记录放进答辩材料。
- 不建议把趋势预测说成精确预测或经营承诺。
- 不建议只展示界面而不展示数据来源、测试或安全边界。
