# 智能 BI 平台 Docker 全栈与用户大模型 API 设计

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 项目 | 智能 BI 数据洞察与报告生成平台 |
| 设计日期 | 2026-07-10 |
| 设计状态 | 已完成方案讨论，等待书面设计复核 |
| 现有版本 | React + Vite 前端原型，使用前端内置示例数据 |
| 目标版本 | Docker Compose 全栈系统，可在本机直接启动和测试 |

## 2. 背景与约束

现有系统已经具备智能查询、仪表盘、报告生成、异常归因和趋势预测页面，但业务数据和分析逻辑主要运行在浏览器内，缺少数据库、后端接口、持久化配置和真实大模型调用能力。

本次升级需要满足以下约束：

1. 使用 MySQL 保存示例业务数据、指标字典、报告模板、查询历史和 AI 配置。
2. 当前电脑没有 MySQL 和 Docker，实施阶段需要获取 Docker Desktop，并由容器提供 MySQL 环境。
3. 用户可以配置自己的 OpenAI 兼容大模型 API，包括 Base URL、API Key 和模型名称。
4. 系统在没有 API Key 时仍能通过本地规则引擎完整演示。
5. 系统需要提供统一启动、停止和测试脚本，减少手工环境配置。
6. 保留现有 React 界面和交互风格，不进行无关的视觉重做。

## 3. 目标与非目标

### 3.1 目标

- 使用 Docker Compose 启动前端、FastAPI 后端和 MySQL。
- 首次启动自动完成数据库迁移和确定性示例数据初始化。
- 将现有页面的数据读取和分析操作迁移到后端 API。
- 提供安全、可测试的用户大模型 API 配置流程。
- 为 Text-to-SQL、报告、异常分析和趋势预测提供可追踪的数据链路。
- 使用单元测试、真实 MySQL 集成测试和浏览器端到端测试证明关键流程可用。

### 3.2 非目标

- 本期不接入企业业务 REST API 作为数据源。
- 本期不建设多租户、注册登录和细粒度权限系统。
- 本期不支持执行任意用户 SQL，也不允许大模型直接执行未经约束的 SQL。
- 本期不训练自有模型，不建设复杂 Agent 工作流。
- 本期不将 Docker 环境部署到公网生产服务器。

## 4. 选定方案

采用 Docker Compose 全套环境：

- `frontend`：React 构建产物由 Nginx 提供，并由 Nginx 代理 `/api`。
- `backend`：FastAPI + SQLAlchemy + PyMySQL，承载 REST API、业务分析和大模型调用。
- `mysql`：使用 `mysql:8.4` LTS 镜像，数据存储在 Docker 命名卷中。
- `mock-llm`：仅在测试配置中启用的 OpenAI 兼容模拟服务，用于验证用户 API 接入链路。

选择 FastAPI 是因为容器已经隔离 Python 环境，不增加用户侧配置成本，同时与原项目 PRD 的技术方向一致。用户日常只需操作 Docker 和 PowerShell 脚本。

## 5. 服务拓扑

```text
Browser
  |
  | http://localhost:8080
  v
Nginx / React (frontend)
  |
  | /api/*
  v
FastAPI (backend)
  |                  \
  | SQLAlchemy        \ HTTPS + Bearer API Key
  v                    v
MySQL 8.4          User OpenAI-compatible API
```

端口约定：

| 服务 | 主机地址 | 用途 |
| --- | --- | --- |
| 前端 | `http://localhost:8080` | 用户访问入口 |
| 后端文档 | `http://localhost:8080/api/docs` | 接口调试 |
| MySQL | `127.0.0.1:3307` | 本机数据库检查和集成测试 |

Compose 使用健康检查控制依赖顺序。MySQL 未健康时后端保持未就绪，后端未健康时前端健康页显示明确状态。

## 6. 后端模块边界

后端按职责拆分，避免路由、SQL 和模型调用混杂在同一文件中：

| 模块 | 职责 |
| --- | --- |
| `api` | 请求校验、响应模型和统一错误映射 |
| `core` | 环境配置、日志、加密和错误类型 |
| `db` | SQLAlchemy 会话、模型、迁移和种子数据 |
| `query` | 查询意图解析、SQL 生成、只读校验和结果整形 |
| `ai` | OpenAI 兼容客户端、配置测试、意图解析和洞察生成 |
| `analytics` | 仪表盘聚合、异常检测和趋势预测 |
| `reports` | 周报、月报、自定义报告和 Markdown 导出 |

各服务通过明确的输入输出模型通信。AI 模块不持有数据库执行权限；它只能返回经过 Pydantic 校验的结构化查询意图或洞察文本。

## 7. 数据库设计

使用 Alembic 管理数据库迁移。后端启动时先执行迁移，再运行幂等种子程序。

### 7.1 `sales_order`

保存示例销售订单，主要字段包括：

- `id`
- `external_order_id`，唯一键，用于幂等初始化
- `order_date`
- `region`
- `province`
- `product_id`
- `product_name`
- `category`
- `customer_type`
- `quantity`
- `amount`
- `profit`
- `created_at`

种子数据至少覆盖连续 18 个月、5 个区域、多个产品类别和客户类型，总记录数不少于 360 条。数据生成使用固定随机种子，保证测试结果稳定。

### 7.2 `metric_definition`

保存销售额、订单量、客单价、销量和毛利等指标的名称、代码、计算表达式、业务说明和启用状态。查询引擎只允许使用这里登记并映射到白名单的指标。

### 7.3 `report_template`

保存周报、月报和自定义报告模板。`sections` 使用 JSON 字段保存模块顺序和开关。

### 7.4 `ai_provider_config`

本期采用单用户本地配置，仅保留一个活动配置：

- `provider_name`
- `base_url`
- `model`
- `encrypted_api_key`
- `api_key_hint`
- `enabled`
- `timeout_seconds`
- `created_at`
- `updated_at`

API Key 使用应用主密钥加密后入库。读取配置接口只返回 `api_key_hint`，不返回密文或明文。

### 7.5 `query_history`

保存问题、解析引擎、结构化意图、生成 SQL、参数、摘要、状态、错误代码、耗时和创建时间。API Key 和数据库密码不进入该表。

## 8. API 设计

所有接口统一使用 `/api` 前缀和 JSON 响应。

| 方法与路径 | 作用 |
| --- | --- |
| `GET /api/health` | 返回应用、数据库、种子数据和 AI 配置状态 |
| `GET /api/metadata` | 返回字段说明、指标字典和可选筛选项 |
| `GET /api/dashboard` | 返回 KPI、趋势、区域和产品聚合数据 |
| `POST /api/query` | 解析自然语言、生成并执行安全 SQL |
| `GET /api/anomalies` | 返回异常点和维度贡献 |
| `GET /api/forecast` | 返回历史序列和基础预测 |
| `POST /api/reports/generate` | 生成报告预览和 Markdown 内容 |
| `GET /api/settings/ai` | 返回脱敏的当前 AI 配置 |
| `PUT /api/settings/ai` | 新建或更新 AI 配置 |
| `DELETE /api/settings/ai` | 删除 AI 配置并切回本地模式 |
| `POST /api/settings/ai/test` | 使用未保存或已保存配置测试模型连接 |
| `GET /api/query-history` | 返回最近查询记录 |

统一成功响应包含 `data` 和 `request_id`。统一错误响应包含 `error.code`、`error.message`、可选的 `error.details` 和 `request_id`。

## 9. 自然语言查询流程

1. 前端提交问题和可选筛选条件。
2. 后端根据 AI 配置决定使用本地解析器或大模型解析器。
3. 解析器返回结构化意图：指标、聚合、维度、时间范围、筛选、排序和数量限制。
4. Pydantic 校验结构和取值，查询服务根据指标字典与字段白名单生成参数化 SQL。
5. SQL 安全层要求单条 `SELECT`，拒绝注释、多语句、数据修改、DDL、授权和未登记表字段。
6. 查询层自动限制最大结果数和执行时间。
7. 后端执行 SQL，生成图表建议、摘要并记录查询历史。
8. 前端展示查询理解、SQL、图表、表格和摘要。

大模型不直接决定最终可执行 SQL。即使模型返回恶意内容，也必须先转换为白名单结构化意图。

## 10. 用户大模型 API 接入

配置页提供以下字段：

- 服务名称
- OpenAI 兼容 Base URL
- API Key
- 模型名称
- 请求超时
- 是否启用

Base URL 接受服务根地址或以 `/v1` 结尾的地址，后端统一规范化后调用 `/chat/completions`。认证使用 `Authorization: Bearer <API_KEY>`。本期不支持任意自定义请求头。

连接测试使用一条最小消息请求，并校验 HTTP 状态和 OpenAI 兼容响应结构。保存配置时：

1. API Key 非空则加密并覆盖旧密文。
2. API Key 留空则保留已有密钥，只更新其他字段。
3. 删除配置时清除整条记录。
4. 前端永远不会读取已保存的明文密钥。

未配置或未启用 AI 时，查询、报告和洞察使用本地确定性逻辑。AI 调用失败时返回明确错误，并允许用户主动切回本地模式；系统不会把回退结果伪装成模型结果。

## 11. 页面改造

- 智能查询：改用 `/api/query`，展示当前解析引擎和查询历史。
- 仪表盘：筛选器改为请求 MySQL 聚合接口，保留现有图表布局。
- 报告生成：改用后端报告接口，保留 Markdown 导出。
- 异常归因：展示后端异常检测结果和数据支持的贡献说明。
- 趋势预测：展示后端历史序列、预测值和“仅供参考”标识。
- 系统配置：新增 AI 服务表单、保存、删除、连接测试和脱敏状态。
- 全局状态：显示后端、MySQL 和 AI 模式状态，加载与错误状态不挤压现有布局。

## 12. 安全设计

- 数据库密码和应用主密钥位于 `.env`，不提交到 Git。
- `scripts/start.ps1` 在缺少 `.env` 时生成随机数据库密码和应用主密钥。
- API Key 使用 Fernet 对称加密后存储，Fernet 主密钥来自环境变量。
- Nginx、后端日志和查询历史均对敏感字段脱敏。
- 后端仅允许已登记的表、字段、指标、排序项和聚合函数。
- SQL 使用绑定参数，禁止将用户输入直接拼接到 SQL。
- 外部 AI 请求启用 TLS 证书校验，默认 30 秒超时，并限制响应体大小。
- 服务端 CORS 仅允许本地前端来源。
- Docker 端口绑定到本机回环地址，不暴露到局域网。

## 13. 错误处理与可观察性

需要区分并展示以下错误：

- Docker 引擎未启动
- MySQL 启动或迁移失败
- 数据库连接失败或查询超时
- 自然语言问题无法解析
- SQL 安全校验拒绝
- AI API 认证失败
- AI 模型不存在
- AI 服务限流
- AI 请求超时或响应格式不兼容

每个请求生成 `request_id`。日志记录请求编号、路由、状态、耗时和错误类型，不记录 API Key、数据库密码或完整敏感请求。`GET /api/health` 返回组件级状态，供页面和启动脚本使用。

## 14. 测试策略

### 14.1 后端单元测试

使用 Pytest 覆盖：

- 本地自然语言意图解析
- 大模型结构化意图校验
- SQL 白名单生成和危险语句拒绝
- API Key 加密、解密和脱敏
- 异常检测
- 趋势预测
- 报告生成
- 错误响应映射

### 14.2 集成测试

使用真实 MySQL 测试容器验证：

- Alembic 迁移
- 幂等种子数据
- 仪表盘聚合
- 自然语言查询到 SQL 执行
- 报告生成
- AI 配置持久化
- 查询历史持久化
- Docker 重启后的数据保留

### 14.3 AI 兼容性测试

测试 Compose 配置启用 `mock-llm` 服务。该服务实现最小 OpenAI `/chat/completions` 协议，用于验证：

- 未保存配置的连接测试
- 保存后的连接测试
- Bearer 认证
- 结构化意图返回
- 认证失败、超时和格式错误
- AI 失败后切换本地模式

### 14.4 前端与端到端测试

保留现有 Node 逻辑测试，并使用 Playwright 验证：

- 打开仪表盘并看到数据库指标
- 提交中文自然语言问题
- 查看 SQL、图表和表格
- 修改维度筛选
- 生成并导出报告
- 查看异常和趋势预测
- 保存、测试、脱敏展示和删除 AI 配置
- 桌面和移动视口无阻断性重叠
- 控制台无未处理错误，关键网络请求均成功

## 15. 启动与测试体验

仓库提供：

- `scripts/start.ps1`：检查 Docker、生成 `.env`、构建并启动服务、等待健康状态并输出访问地址。
- `scripts/stop.ps1`：停止容器但保留 MySQL 数据卷。
- `scripts/reset.ps1`：经用户明确确认后删除本项目数据卷并重新初始化。
- `scripts/test.ps1`：启动测试服务并运行后端、前端、集成和端到端测试。

正常启动命令：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start.ps1
```

启动完成后访问 `http://localhost:8080`。MySQL 由 Docker 自动拉取和运行，不要求本机单独安装 MySQL Server。

## 16. 验收标准

以下条件必须全部满足：

1. Docker Desktop 安装并启动后，执行一个启动脚本即可运行系统。
2. Compose 中的前端、后端和 MySQL 均通过健康检查。
3. 首次启动自动创建数据库结构并导入不少于 360 条示例订单。
4. 再次启动不会重复导入示例数据，停止再启动后数据仍存在。
5. 六个主要页面均从后端或 MySQL 获取真实数据并可操作。
6. 不配置 API Key 时，自然语言查询、报告、异常和预测均可演示。
7. 用户可以保存、测试、修改和删除 OpenAI 兼容 API 配置。
8. 测试用模拟 API 能证明连接、认证、模型调用和错误回退链路。
9. 用户提供真实兼容 API 后，可通过配置页完成连接测试并用于查询或报告洞察。
10. API Key 不出现在前端响应、浏览器日志、服务日志或 Git 跟踪文件中。
11. 危险 SQL、非白名单表字段和多语句查询均被拒绝。
12. 后端单元测试、MySQL 集成测试、前端测试和关键浏览器流程全部通过。
13. README 明确记录安装、启动、停止、重置、测试和 API 配置步骤。

## 17. 实施顺序

1. 添加 Compose、环境模板、FastAPI 骨架和健康检查。
2. 添加 MySQL 模型、Alembic 迁移和幂等种子数据。
3. 以测试驱动方式实现查询意图、SQL 安全层和查询 API。
4. 实现仪表盘、异常、预测和报告 API。
5. 实现 AI 配置加密、连接测试和 OpenAI 兼容客户端。
6. 将 React 页面切换到后端 API，并补齐加载、错误和配置交互。
7. 添加模拟 AI、真实 MySQL 集成测试和 Playwright 端到端测试。
8. 完成 PowerShell 脚本、README、Docker Desktop 环境获取和本机验收。
